Como o código funciona, passo a passo

O sistema tem duas fases. Primeiro, um script monta a base de conhecimento a partir das fontes. Depois, a cada pedido do usuário, os agentes trabalham em cima dessa base: o Montador propõe, o Avaliador verifica e o laço de rodadas junta os dois.

1

Montar a base de conhecimento

A base não é editada à mão: o script construir_base.py refaz tudo a partir de fontes/, então qualquer correção fica registrada no Git.

  1. Lê as receitas do Ministério da Saúde, as do grupo e as geradas por IA.
  2. Traduz cada ingrediente escrito ("cebola picada em cubos pequenos") para um id da base (cebola), por uma lista de trechos de texto. Temperos como sal e cheiro-verde são ignorados.
  3. Converte a medida caseira em gramas com medidas.py: volume da medida × densidade do ingrediente, ou número de unidades × peso médio da unidade.
  4. Divide pelo rendimento da receita e grava tudo para 2 porções, o padrão do sistema.
  5. Liga cada ingrediente à TACO para ter kcal, proteína, fibra e sódio por 100 g.
  6. Calcula as tags de restrição de cada receita a partir dos ingredientes.
  7. Recusa terminar se alguma receita usar um ingrediente sem cadastro, e escreve o relatório kb/RELATORIO_BASE.md.

2

Perfil e Guardião

O Perfil guarda o que vale para a pessoa: restrições (regras rígidas), tempo máximo, quantas pessoas comem, gostos e os pesos que dizem o que importa mais para ela. O Guardião transforma as restrições num conjunto de ingredientes proibidos, consultando a tabela restricoes.csv.

agentes.py 
def proibidos(self, perfil: Perfil) -> set:
    out = set()
    for r in perfil.restricoes:                  # ex.: ["vegetariano", "sem_lactose"]
        out |= self.restricoes.get(r, set())     # junta os ingredientes proibidos de cada uma
    return out

É uma consulta a uma tabela, não uma decisão do LLM. Por isso a mesma restrição sempre bloqueia os mesmos ingredientes.

3

Agente Montador: propor receitas

O Montador só propõe; quem decide é o Avaliador. Ele tem dois modos com a mesma saída (uma lista de receitas em JSON), e cai sozinho no modo base se o LLM falhar.

montador.py 
def propor(self, perfil, estoque, feedback, n=6):
    if self.modo == "llm":
        try:
            receitas = self._propor_llm(perfil, estoque, feedback, n)
            if receitas:
                return receitas
        except Exception as e:                   # API fora, JSON quebrado etc.
            self.log.append(f"falha no LLM ({type(e).__name__}); usando a base")
    return self._propor_base(perfil, estoque, feedback, n)

Modo LLM. O prompt leva a lista de ingredientes permitidos (os proibidos já saíram), o tempo máximo, o estoque, dois exemplos de receita em JSON e todos os motivos de rejeição acumulados. Da resposta, o código recorta só o array JSON e descarta receitas fora do formato.

Modo base. Percorre as receitas da base e adapta cada uma ao perfil:

proteinas = {i: g for i, g in r["itens"].items() if self.ing[i]["categoria"] == "proteina"}
if proteinas and max(proteinas, key=proteinas.get) in evitar:
    return None      # "frango ensopado" sem frango não serve: descarta
...
sub = next((s for s in self.subs.get(i, [])
            if s == "remover" or (s not in evitar and s in self.ing)), None)
  1. Pula acompanhamentos e receitas mais demoradas que o tempo do perfil.
  2. Se a proteína principal for proibida, descarta a receita.
  3. Troca os outros ingredientes proibidos pelo primeiro substituto permitido da tabela (leite → bebida vegetal) ou os remove (bacon, paio). Se não houver saída, descarta.
  4. Ordena pelo aproveitamento do estoque, com uma pequena penalidade por troca, para preferir receitas originais.

Agente Avaliador: verificar e pontuar

O Avaliador não confia no Montador. Faz as checagens na ordem, da mais barata para a mais cara, e só dá nota a quem passa em todas.

avaliador.py 
for checagem in (self._formato, self._ingredientes_existem):
    motivos = checagem(r)
    if motivos:
        return Resultado(r, False, motivos=motivos)
motivos = self._restricoes(r, perfil) + self._quantidades(r)
if r["tempo_min"] > perfil.tempo_max_min:
    motivos.append(f"demora {r['tempo_min']} min; o máximo do perfil é {perfil.tempo_max_min}")
if motivos:
    return Resultado(r, False, motivos=motivos)

c = self._caracteristicas(r, perfil, estoque)        # 5 valores entre 0 e 1
nota = sum(pesos[k] * v for k, v in c.items())        # soma ponderada pelos pesos do perfil
  • Checagens: formato do JSON, ingredientes existentes na base, restrições (veto), porção por pessoa dentro do limite da categoria, tempo.
  • Características da nota: quanto é comida in natura (descontando ultraprocessados), se tem verdura ou fruta, gosto da pessoa, rapidez e aproveitamento do que vai estragar.
  • Explicação: as duas características que mais somaram viram a frase ("tem verdura ou fruta, é rápida").
  • Nutrientes: soma os valores da TACO de cada ingrediente e divide pelas porções.
5

O laço entre os dois agentes

A função planejar repete até 3 rodadas. Em cada uma, pede ao Montador só o que falta, o Avaliador julga, e os motivos de rejeição se acumulam, para o Montador não corrigir um erro e reintroduzir outro.

planejamento.py 
for rodada in range(1, max_rodadas + 1):
    faltam = n - len(aprovadas)
    propostas = montador.propor(perfil, estoque, feedback, n=faltam + 2)  # margem
    ok, motivos, todos = avaliador.avaliar_lote(propostas, perfil, estoque)
    ...
    feedback["motivos"] = sorted(set(feedback["motivos"]) | set(motivos))  # acumula
    if len(aprovadas) >= n:
        break

Se não fechar em 3 rodadas, o status diz quantas receitas faltaram. A ideia é a interface mostrar as alternativas para a pessoa decidir, em vez de o sistema insistir.

6

Aprendizado com o retorno da semana

Depois da semana, a pessoa diz o que fez. A função compara cada característica com a média das sugestões e mexe só no peso do que diferencia o que foi feito do que não foi. O experimento 4 mostra por que isso é melhor que somar a característica direto.

media = {k: sum(c[k] for c in caracteristicas.values()) / len(caracteristicas) for k in chaves}
for nome, c in caracteristicas.items():
    sinal = 1 if nome in feitas else -1
    for k in chaves:
        perfil.pesos[k] = min(maximo, max(minimo, perfil.pesos.get(k, 1.0) + taxa * sinal * (c[k] - media[k])))

Os pesos ficam entre 0,2 e 3, para um retorno isolado não distorcer o perfil. Restrições nunca são aprendidas: só mudam quando a pessoa edita.

7

Receitas de IA com curadoria

gerar_receitas_llm.py pede ao LLM receitas para lacunas definidas (rápida para quem mora sozinho, vegetariana com leguminosa, marmita, baixo custo, sem lactose e sem glúten, nordestina). Cada uma passa pelo mesmo Avaliador, com as restrições da lacuna.

  1. Aprovadas vão para fontes/receitas_llm.csv com revisado_pelo_grupo=nao.
  2. Rejeitadas vão para receitas_llm_rejeitadas.csv com os motivos, para melhorar o prompt.
  3. O grupo revisa, marca sim e roda construir_base.py. Antes da entrega, só as revisadas entram.
8

Como os experimentos foram simulados

  • Experimento 1: para cada combinação de restrições, conta os pratos sem nenhum ingrediente proibido e os que o Montador consegue adaptar.
  • Experimento 2: pega pratos válidos, injeta um erro de cada tipo (300 receitas por tipo) e conta quantos o Avaliador rejeita. O grupo de controle não recebe erro.
  • Experimento 3: um "LLM" de mentira devolve receitas reais da base, cada uma com um erro com probabilidade p. Ele não aprende com os motivos, então é o pior caso. 200 simulações por taxa.
  • Experimento 4: 60 usuários com um gosto escondido (querem rapidez, comida in natura ou verdura no prato). A pessoa "faz" uma sugestão se ela estiver entre as 20% melhores para o gosto dela. 12 semanas, 5 sugestões por semana.
  • Experimento 5: nutrientes por pessoa de cada prato, calculados pela TACO a partir dos ingredientes crus.
